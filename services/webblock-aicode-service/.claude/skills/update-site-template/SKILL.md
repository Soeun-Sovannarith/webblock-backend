# Update the generated-site templates

Rules: `.claude/rules/site-templates.md`. These files ship into every customer site, not into this service.

1. **Check the framework docs first.** The site uses Next.js 16 / React 19 (`app/templates/site/package.json`), which is newer than most training data. Check the Next.js 16 docs before you touch routing, `generateStaticParams`, metadata, `params` (async in Next 15+) or config.
2. **Know who receives the change.**

   | File | Reaches |
   |---|---|
   | `scaffold.REFRESHED_TEMPLATES`: `app/[[...slug]]/page.tsx`, `components/blocks/theme.ts`, `theme.css`, the fullstack files (`scaffold.FULLSTACK_PATHS`: `lib/db.ts`, `lib/products.ts`, `lib/business.ts`, `lib/portal-auth.ts`, `app/portal/*`, `portal/*`, `app/media/*`, `package.json`) and the runtime files | every existing site on its next update |
   | `scaffold.REMOVED_TEMPLATES` (a template file you delete) | deleted from every existing site on its next update |
   | `db/schema.ts` | new sites; existing sites only get the `products`, `portal_revoked_sessions` and `business_profiles` tables added (`drizzle_generator.ensure_site_tables`). It only describes the shared `site_data` tables: a new table or column also needs a `sql/00N` migration (`.claude/rules/sql-migrations.md`) |
   | Block components | new sites, or existing ones only through `ensure_blocks`/GLM |
   | `components/registry.tsx` | nobody directly: it is generated by `scaffold.render_registry`, so edit the Python |
   | `scaffold.HARNESS_OWNED` files | GLM can never patch these per project, so they must be correct on their own |

   Tell the user which sites will (and won't) get the change.
3. **Keep the editor contract.** Block files import only `react` and use `wb-` classes (the template-check hook enforces this). Style props are applied through `theme.ts` `blockAttributes`/`siteAttributes` → `data-*` → `theme.css`.
4. **Unit tests**: `pytest tests/test_scaffold.py` (rendering, registry, catalog parity).
5. **Real build.** This is the only true check:
   - Make sure Docker is up (`docker info`) and `BUILD_RUNNER=docker` is set in `.env`.
   - Run a generation (see the `run-e2e-local` skill), then read the run's `validation_runs` (`INSTALL`, `BUILD`) and `run.log`.
   - For a change that reads or writes data, run the site against the compose database's `site_data` schema: `python scripts/e2e_onboarding.py --serve` registers and seeds a tenant and checks `/readyz` and the pages.
   - If Docker isn't available, say the build was not verified. Don't claim it passes.
6. `package.json` is recopied into every existing site, so a dependency bump reaches all of them on their next update. `npm install` runs with `--ignore-scripts`, and with network only in `INSTALL`. Get the user's OK first.
