# Generated-site templates

These files are not code for this service. They are copied verbatim into every generated Next.js 16 / React 19 site. They are built only by the pipeline's `BUILD` step (`BUILD_RUNNER=docker|local`), never in this repo.

**What reaches existing sites:**
- Only `scaffold.REFRESHED_TEMPLATES` are recopied into existing sites on every update: `app/[[...slug]]/page.tsx`, `components/blocks/theme.ts`/`theme.css`, the fullstack files (`scaffold.FULLSTACK_PATHS`: `lib/db.ts`, `lib/storage.ts`, `lib/media.ts`, `lib/products.ts`, `lib/business.ts`, `lib/portal-auth.ts`, the portal directories `scaffold.PORTAL_DIRS` including the SSO and media routes, `db/schema.ts`, `package.json`) and the runtime files (`scaffold.RUNTIME_PATHS`). `db/seed.sql` is rendered on every run (`scaffold.render_seed_sql`).
- To drop a template file from existing sites, delete it from the templates and add its path to `scaffold.REMOVED_TEMPLATES` (now `drizzle.config.ts`, `db/seed.mjs`): `refresh_templates` deletes those paths on the next update, and they stay harness-owned so GLM can't bring them back.
- A block file such as `Hero.tsx` is copied only into new sites, or into a site that lacks it (`scaffold.ensure_blocks`). A fix to an existing block reaches existing sites only through a GLM update.
- `components/registry.tsx` is generated by `scaffold.render_registry`. Change it there; there is no template file for it.
- Never add `app/page.tsx`: it clashes with the catch-all route, and `glm.RESERVED_PATHS` blocks it.
- **Provisioning's runtime contract** (README section 10.2) is met by `scaffold.RUNTIME_PATHS`, all harness-owned:
  - The `Dockerfile` and `.dockerignore`. The Dockerfile builds `output: "standalone"` from `next.config.mjs` and runs `node server.js` on `0.0.0.0:8080` as UID 65532, with a read-only root where Next.js's cache dir links to `/tmp`.
  - `package-lock.json`, for `npm ci`. Regenerate it whenever `package.json` changes: `npm install --package-lock-only --ignore-scripts` in a `node:22-alpine` container on a copy holding only `package.json`.
  - `app/healthz/route.ts`: 200, never touches the database.
  - `app/readyz/route.ts`: `catalogIsReachable()` (a `products` query, then the role must map to an active website, else `UNKNOWN_WEBSITE`) within 2 s, else 503; log the error code only.

  `app/healthz/` and `app/readyz/` are harness-owned directories, and `/healthz` and `/readyz` are reserved page paths. Never read the database at build time: the platform's build has none.
- **The site's data lives in the shared `catalog` schema** of this service's database (`sql/007_catalog.sql`, `app/services/site_catalog.py`, README section 6 "Generated site database"), never in a database of its own.
  - Only `lib/db.ts` connects. It reads the libpq variables `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, `PGSSLMODE` (or `DATABASE_URL` for local work), logs in as the site's own role `site_<project uuid hex>` and sets `search_path=catalog`; `currentWebsiteId()` gives the website. Never log a value.
  - Write site SQL against the unqualified catalog tables and never name `website_id` in an insert or a filter: the column defaults to `current_website_id()` and row-level security (`website_isolation`) limits every read and write to the role's website. Never write DDL, and never add a schema push or seed runner to the site: the role can't create tables, and the harness seeds the site in `DEPLOY` (`site_catalog.prepare_site`).
  - Only `UPDATE` `business_profiles`: sites have no `INSERT` on it (the harness inserts every website's profile) and no write on `websites`.
  - `db/schema.ts` is a harness-owned template (`pgSchema("catalog")`, `scaffold.catalog_schema()`), the same for every site, so keep it and `sql/007_catalog.sql` in step. A table or column the site needs needs a new `sql/00N` migration (`website_id` with the `current_website_id()` default, the `website_isolation` policy, grants to `webblock_site`) and the template change; `tests/test_site_catalog.py` checks the migration's tables and columns against the design (`DESIGN`/`EXTENSIONS`) and against `db/schema.ts`.
  - Write `ON CONFLICT` targets against the real keys, which include `website_id` (for example `portal_revoked_sessions`' primary key is `(website_id, sid)`, so `portal-auth.ts` uses a bare `ON CONFLICT DO NOTHING`).
  - **Images and the logo live in object storage, not the database** (`lib/storage.ts`: AWS Signature V4 with `node:crypto` only; keys `websites/<website_id>/<folder>/<uuid>.<ext>`). Rows keep only `storage_key` and `byte_size`, and the `track_storage` trigger enforces the limits: map its refusals to owner messages with `storageProblem()` (`ck_websites_max_image_bytes`, `ck_websites_storage_within_limit`). Serve files only through `lib/media.ts` (`app/media/products/[id]`, `app/media/logo`), which sends a sandbox CSP and `nosniff` and anything not an image as an attachment, because the bytes are owner uploads. Without `STORAGE_*` settings, refuse uploads with a message and let new products be added without a photo.
- **The site is fullstack.** With database settings, the page route reads the `products` table at request time (`connection()` + `listProducts`, both pages and `/products/<slug>` detail pages are dynamic) and passes the rows to every `ProductCards` block as `products`. Without it, it falls back to the products in `puck-data.json`. Keep that fallback, because the build sandbox has no database. A Puck page with the same path wins over a product.
- **Product portal (`app/portal`).** Owners sign in with single sign-on: `lib/portal-auth.ts` plus the `app/portal/login`, `callback` and `backchannel-logout` routes; the rules are in `.claude/rules/portal-sso.md`. Owners add, hide and delete products and edit the business details through server actions; the portal adapters pass uploads as `Photo` objects (`portal/lib/files.ts` `imageToPhoto`). Every action calls `requireOwner()` itself, because a server action can be invoked without loading the page. The write functions in `lib/products.ts` check the session again (`ownerSql`), so a route GLM adds later can't change the catalog without a signed-in owner. GLM can still read `lib/db.ts`'s connection, so this is defence in depth, not a boundary. `glm.validate_changes` rejects anything under `app/portal/` and any `.ts`/`.tsx` sibling of a harness-owned module (`glm.HARNESS_MODULES`; the bundler would resolve the `.tsx` first). Write SQL only as `postgres` tagged templates in `lib/products.ts`, never `sql.unsafe` with user input. `/portal` is reserved (`catalog.RESERVED_PAGE_PATHS`).
- `productSlug` lives in `lib/products.ts` and is repeated in `ProductCards.tsx` because blocks may import only React. Change both together (`tests/test_scaffold.py` compares them). Detail-page styles go in `theme.css`, not `blocks.css`, so existing sites receive them on their next update.

**Block components (`components/blocks/<Type>.tsx`):**
- Follow `Text.tsx`: `export type <Type>Props = {...}` with every prop optional, a default for each in the destructuring (Puck can omit any prop), and one `export default function <Type>`.
- Import only from `react`. The editor frontend copies these files into its preview.
- Wrap markup in `<section className="wb-section wb-<type>">` with `<div className="wb-container">`. Styles go in `blocks.css`, and every class starts with `wb-`.
- Ignore `tone`/`align`/`spacing`/`id`: the registry wrapper turns style props into `data-*` attributes (`theme.ts` `blockAttributes`), and `theme.css` styles them.
- The file name must equal the catalog type (`scaffold.block_path`). `tests/test_scaffold.py` asserts that the implemented types equal `CATALOG`.

GLM may later rewrite any non-harness-owned file in a project's copy, so keep components small and readable.
