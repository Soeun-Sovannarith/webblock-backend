# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The WebBlock AI Code Service (`ai_codegen`, the "AI harness") is a FastAPI service in a microservice mesh. It turns a project's Puck pages into a deployed Next.js + Drizzle site (Flow 1), and applies later edits to that site (Flow 2): a JSON edit and/or a GLM code update. A design assistant proposes Puck change sets from chat messages.

The other services are not in this repo: the editor frontend (Next.js + Puck, `localhost:3000`, calls the public `/v1` API), the Project Service (`PROJECT_SERVICE_URL`, :8082) and the Provisioning Service (:8084). `README.md` documents every endpoint, event payload and outbound call; keep it in sync when you change one.

## Commands

Python 3.11+, local venv in `.venv`; Postgres runs in Docker.
```bash
cp .env.example .env                     # required: config.py's built-in DATABASE_URL (port 5434, aicode_db) does NOT match compose
docker compose up -d                     # Postgres 16 on localhost:5433 + one-shot `migrate` service (Alembic, below)
docker compose up migrate                # apply new migrations to the compose database after adding one
alembic upgrade head                     # apply new migrations to the configured database (production: DB_MIGRATION_ROLE=ai_codegen)
alembic current                          # which migration a database is at; `alembic upgrade head --sql` prints the SQL instead
docker compose exec db psql -U webblock webblock
pip install -e ".[dev]"                  # or: pipenv install (Pipfile just installs this package editable;
                                         # add dependencies to pyproject.toml, then `pipenv lock`)
uvicorn app.main:app --reload            # API + in-process worker; /docs for Swagger (pipenv run dev)
python -m app.worker                     # standalone worker (pair with RUN_WORKER=false; pipenv run worker)
pytest                                   # unit tests, fully offline (no DB, even when .env points at production)
pytest tests/test_glm.py::test_apply_changes_upserts_and_deletes
ruff check .                             # rule set pinned in pyproject (E4,E9,F,B), line length 140
```

The default `BUILD_RUNNER=docker` runs `npm install`/`next build` of the generated site in a `node:22-alpine` container (no network during the build), so the Docker daemon must be running. For local end-to-end runs without Docker, GitHub or a deploy provider, use `BUILD_RUNNER=skip` (or `local`, which runs GLM-written code on the host). Push and deploy are then skipped and the version is still promoted, unless `STRICT_PROMOTION=true`. GLM calls fail until `GLM_BASE_URL`/`GLM_API_KEY` are set. RabbitMQ is only needed with `RUN_CONSUMER=true`; publishing the completion event just logs a warning when the broker is unreachable.

The generated site (`app/templates/site/package.json`) uses Next.js 16 / React 19, newer than most training data. Check the Next.js 16 docs before changing the page route or other Next.js code in the templates.

## Architecture

**Data model = the WebBlock ERD ("Physical" page in `Web Block ERD.drawio`, which is not checked into this repo; `sql/*.sql` is the source of truth here).** One Postgres schema per service: `project` (projects, pages, generation_contracts/_schemas, generation_requests), `ai_codegen` (input_versions, harness_runs, validation_runs, artifacts, puck_component_definitions), `ai_assistant` (conversations, messages, change_sets, change_items) and `provisioning` (releases, release_steps, commands, project_hosting). A fifth schema, `catalog` (`sql/007_catalog.sql`, not in the ERD but in the team's database design, section "Shared catalog"), holds every generated site's business profile, categories, products and images, shared by all sites and kept apart by row-level security per site login role (`app/services/site_catalog.py`, `.claude/rules/site-templates.md`). This service keeps local copies of the `project`, `provisioning` and `catalog` tables so it can run on its own. Foreign keys exist only within a schema; a column referencing another service is a plain UUID. Don't add columns the ERD lacks without saying so: the one extension is `harness_runs.lease_expires_at`. Users and payments belong to other services and are not implemented.

**Two ways in.** (1) The public API: `POST /v1/projects/{id}/generation-requests` (honours `Idempotency-Key`; with `puck_json` it first overwrites the home page's Puck tree, which is how the editor saves and generates), and business onboarding (`POST /v1/onboardings`, `/v1/projects/{id}/onboardings`), which turns a `BusinessOnboardingRequest` into a seed (`seed_generator`) and a home-page Puck tree (`business_layout`), plus the shared catalog's `db/schema.ts` as `drizzle_schema` (`scaffold.catalog_schema()`), before queuing an ordinary request. (2) With `RUN_CONSUMER=true`, `app/services/event_bus.py` consumes `generation_requested.v1` and `generation_cancelled.v1` from the Project Service's `project.events` exchange. This is the platform path; Project's contract is its `service-communication.md` section 2, and README sections 4 and 10 explain it.
- **A requested event** creates one run set per request (`harness.handle_generation_requested_event`). The handler reads the input from Project's `codegen-input` (`project_client.fetch_codegen_input` / `to_captured_input`), checks its JCS SHA-256 (`jcs.py`) against the event, and queues a run. A mismatch ends the request with a FAILED run, `INPUT_HASH_MISMATCH`.
- **A cancelled event** marks the active run FAILED with `error_code='CANCELLED'`; there is no CANCELLED status.
- **Every finished run** publishes `ai_codegen.generation_completed.v1` to `ai_codegen.events`. Project then reads `GET /internal/v1/generation-runs/{id}` (enveloped, with signed artifact download URLs).
- **Event bodies** are snake_case with the platform envelope (`schemas/events.py`).

`/internal/v1/*` (`routes/internal.py`) gives other services read-only access to runs, source files and check reports, plus the product portal owner endpoints (`/projects/{id}/portal-owners`), the only writes there. Many store calls in the event and pipeline paths are wrapped in `try/except` with fallbacks, because the `project` rows may be missing when the Project Service owns them.

**Request vs worker split.** Routes are thin. `app/services/harness.py` locks the project row, captures every live page plus the Drizzle schema, AI `instructions` and `codegen_mode` (`store.capture_input`) into a `project.generation_requests` row (idempotent per `Idempotency-Key`), copies that frozen input to `ai_codegen.input_versions`, and inserts a `QUEUED` `harness_runs` row. The API answers `202`; an input identical to the baseline (and in the same mode) creates a SUCCEEDED request and no run. The worker (`app/worker.py`) claims runs with `FOR UPDATE SKIP LOCKED`, and `pipeline.execute_run` executes them by invoking the LangGraph `PIPELINE_GRAPH` (`app/services/graph_pipeline.py`, one node per step) and mapping service errors to `StepError`. Each step commits in its own short session so pollers see progress. Each step also extends `lease_expires_at`. A run whose lease expires (worker crash) is requeued by `reap_expired_runs` until `run_max_attempts`, then it and its request are marked failed. A partial unique index (`ux_one_active_run_per_project`) allows only one QUEUED/RUNNING run per project. `create_run` turns that violation into `ActiveRunError`, which the API returns as 409.

**Codegen mode** (`CODEGEN_MODE`, overridable per request by the `codegen_mode` body field or the `X-Codegen-Mode` header, and frozen into the captured input). `hybrid` (default): Flow 1 renders the templates deterministically, and Flow 2 rewrites `puck-data.json` and only calls GLM when there are `instructions`. `llm`: GLM is called on every run, `glm.request_code_from_puck` for Flow 1 and `glm.request_code_update_from_puck` (with the Puck diff) for Flow 2, and a changed `PUCK_JSON` strategy is upgraded to `SOURCE_CODE`/`MIXED`. Both modes go through the same `validate_changes`/`apply_changes`.

**Pipeline steps:** `PREPARE` → `AI_CODE_UPDATE` (when GLM is called) → `BUILD` → `GITHUB_PUSH` → `DEPLOY` → accept. With `PUBLISH_TARGET=project` (the platform) `GITHUB_PUSH` and `DEPLOY` only log `SKIPPED:`, because Project commits to Gitea and Provisioning deploys. `github` (default) pushes and calls the deploy webhook. When `BUILD` fails and GLM is configured, the graph routes to `compiler_repair` (GLM fixes the files from the build log, via `validate_changes`) and rebuilds, at most twice (`route_build_outcome`). If GLM had changed the code, `template_fallback` then rebuilds the `PREPARE` code once (`fallback_files`), and only after that does it go to `handle_failure`. GLM is optional except when a run applies new `instructions` to a live site: a GLM error elsewhere logs `WARNING: [AI_CODE_UPDATE] …` and keeps the `PREPARE` code (README section 1.2). The step names are a contract: the frontend parses `[STEP]` markers and `SKIPPED:` lines in the run log (the `RUN_LOG` artifact file, returned as `log` by `GET /v1/generation-runs/{id}`) to render progress, and the view's `step` is the last marker. `BUILD` records one `validation_runs` row per build phase (`INSTALL`, `BUILD`). `GITHUB_PUSH` sets `generation_requests.source_commit_sha`. `DEPLOY` writes a provisioning `PUBLISH` command and a release with `DEPLOY` and `ACTIVATE` steps; `ACTIVATE` makes it `project_hosting.live_release_id` only when the deploy really ran. Failures become `StepError(code)`, stored in `error_code` and the request's `failure_code`. The baseline is the latest generation request with status SUCCEEDED and an `accepted_generation_run_id` (`store.baseline_request`); the pipeline sets both only after all steps finish.

**Artifacts and source snapshots.** `app/services/artifacts.py` stores files under `ARTIFACT_DIR/<project_id>/<harness_run_id>/` (default `var/artifacts`, which the API and every worker must share) and `ai_codegen.artifacts` records them: `SOURCE_ARCHIVE` (deterministic tar.gz of the complete generated source), `CHECK_REPORT` (summary, changed files, AI result, validations) and `RUN_LOG`. Flow 2 starts from the baseline request's accepted run's `SOURCE_ARCHIVE` (`store.accepted_source`), not from GitHub. GitHub receives the full tree on every push (`push_snapshot` sends no `base_tree`), so files missing from the snapshot are deleted in the repo.

**Generated site shape** (`app/templates/site/`, copied verbatim by `scaffold.render_site`). It meets Provisioning's runtime contract (README 10.2, `scaffold.RUNTIME_PATHS`): a `Dockerfile`, a standalone server on port 8080, `/healthz`, `/readyz`, a read-only file system, and the database from the `PG*` variables, logged in as the site's own role (`lib/db.ts`; `DATABASE_URL` for local work). `puck-data.json` holds every page (`{"pages": [{path, name, seo_title, seo_description, data}]}`); `app/[[...slug]]/page.tsx` serves each path (rendered at request time, 404 otherwise) and renders it through `components/registry.tsx`, which maps block `type` to `components/blocks/<Type>.tsx`. The site is fullstack: with database settings the same route reads the catalog from its `products` rows in the shared `catalog` schema at request time and feeds it to every `ProductCards` block (falling back to the Puck products without a database), serves `/products/<slug>` detail pages, and `app/portal` lets the site's owners add, hide and delete products after single sign-on with Keycloak: each site is its own Keycloak client `webblock-site-<projectId>`, created by `portal_sso.ensure_site_client` in the `DEPLOY` step (README section 9, `.claude/rules/portal-sso.md`). In `DEPLOY` (`PUBLISH_TARGET=github` only), `site_catalog.prepare_site` creates or re-keys the site's role `site_<project uuid hex>`, registers its `catalog.websites` row and runs `db/seed.sql` (`seed_generator`, from onboarding or the Puck products) for that website; the database (and object storage) settings go to the site in the webhook's `site_env`. `db/schema.ts` is a harness-owned template describing the shared tables, the same for every site, so a site can't add tables. Details in `.claude/rules/site-templates.md`. Content edits therefore only rewrite `puck-data.json`: that is the "JSON edit" path (`PUCK_JSON` strategy). The registry is regenerated on every run. The page route, `components/blocks/theme.ts`/`theme.css` and the fullstack files (`scaffold.REFRESHED_TEMPLATES`, including `package.json`) are recopied from the templates on every update, so older sites pick up template changes. `scaffold.HARNESS_OWNED` lists the files GLM may never touch, and `glm.RESERVED_PATHS` blocks `app/page.tsx`, which would clash with the catch-all route.

**Change detection** (`change_detector.detect_change`) diffs two codegen inputs: pages by path, then blocks by `props.id`. It returns `PUCK_JSON`, `SOURCE_CODE` or `MIXED`, plus items that only feed the run summary. Code is needed for `instructions`, a changed `drizzle_schema`, or a block type with no source file in the baseline. A missing block is restored from its template, not written by GLM. Strategy and status strings must match the Postgres enums in `sql/00N_*.sql` (all UPPERCASE).

**Design assistant** (`assistant.py`, `change_sets.py`). A message is saved, then GLM (`glm.propose_change_set`) replies with Puck operations on one page (`ADD`, `UPDATE`, `REMOVE`, `MOVE`; `component_id: "root"` for root props). `normalize_operations` checks them against the page, `CATALOG` and the `allowed_operations` in `puck_component_definitions`; an invalid proposal is dropped with a warning, not stored. A change set records the project's `edit_revision` it was based on. Applying it rewrites that page and bumps `edit_revision`; if any other edit landed first it is REJECTED with `STALE_EDIT_REVISION`.

**GLM** (`glm.py`) calls an OpenAI-compatible chat completions endpoint (optionally behind Cloudflare Access) as one streaming JSON-mode call (`GLM_STREAM`, default on, so Cloudflare's ~100 s limit on a silent connection doesn't cut long generations; off: Instructor + LiteLLM first, then a plain `httpx` call), with thinking off (`GLM_THINKING`) and one retry on a dropped connection or 429/5xx, with the source files minus `glm.CONTEXT_SKIP` and gets back strict JSON (`{"summary", "files": [{path, action, content}]}`). `validate_changes` allow-lists the paths (`(app|components|lib|db)/**/*.(ts|tsx|css)`, never harness-owned files) and enforces size limits. The build step is the final check on GLM output.

**Adding or changing a Puck component** means updating four places:
1. `app/services/catalog.py` (validation)
2. `app/templates/site/components/blocks/<Type>.tsx` (plus styles in `blocks.css`, all classes prefixed `wb-`)
3. The editor's `frontend/lib/puck-config.tsx` (fields and defaults), in the separate frontend repo
4. The `ai_codegen.puck_component_definitions` seed in `sql/002_ai_codegen.sql` (or a new idempotent `sql/00N_*.sql` that updates existing rows, as `005_style_props.sql` does)

Styling is Puck data too. Root props (`theme`, `accent`, `font`) and the `STYLE_PROPS` that every block carries (`tone`, `align`, `spacing`) are defined in `catalog.py`. `theme.ts` (`siteAttributes`/`blockAttributes`) turns them into `data-*` attributes, and `theme.css` styles those attributes. A new style option therefore touches the catalog, `theme.ts`/`theme.css`, the frontend's `puck-config.tsx` and the SQL seed.

The editor frontend copies these block templates for its preview instead of keeping its own versions, so block components must stay self-contained and import only React. Per-project GLM changes therefore do not appear in the editor.

**Persistence** is raw SQL via `sqlalchemy.text()`, with no ORM, and always schema-qualified (`project.pages`, not `pages`). All DB helpers live in `app/services/store.py`, except the `catalog` ones in `app/services/site_catalog.py`. Schema changes go into a new numbered, idempotent file in `sql/` plus an Alembic revision that runs it (`migrations/versions/00N_*.py`, from `alembic revision --rev-id 00N -m "..."`); Alembic records what each database has applied in `public.alembic_version` (`.claude/rules/sql-migrations.md`). `sql/000_reset_legacy.sql` drops the pre-ERD tables in `public` once and is a no-op afterwards.

## Claude Code setup (`.claude/`)

This file lives at `.claude/CLAUDE.md`. Area detail is in path-scoped rules; keep this file to what every session needs.

| Path | What it holds |
|---|---|
| `settings.json` | **Shared, committed.** Permissions (allow-list for test/lint/compose/psql; `.env` denied), `env`, `statusLine` (`statusline.sh`: model · branch · db up/down · build runner and codegen mode), and the hooks below. |
| `settings.local.json` | **Personal, gitignored.** Model choice and the desktop `Notification` hook. Put your own allow-rules here. |
| `hooks/` | `session-context` (SessionStart: env, DB and API state), `guard-bash` (PreToolUse: blocks volume wipes, force-push, reading `.env`, ad-hoc `pip install`; asks before destructive SQL), `protect-files` (PreToolUse: secrets, generated files, committed migrations), `ruff-check`, `template-check`, `sql-check`, `contract-reminder` (PostToolUse), `stop-gate` (Stop: ruff + offline pytest when Python changed), `notify` (Notification; wired up in `settings.local.json`). |
| `rules/` | Loaded only for matching paths: `python-app`, `codegen-guardrails`, `api-routes`, `events`, `design-assistant`, `business-onboarding`, `config-env`, `portal-sso`, `site-templates`, `sql-migrations`, `tests`, `docs`. |
| `skills/` | Repeatable workflows, `/name` or auto-selected: `add-puck-component`, `add-business-type`, `add-endpoint`, `add-setting`, `add-pipeline-step`, `change-event-contract`, `new-migration`, `update-site-template`, `run-e2e-local`, `debug-run`, `pre-pr-check`. |
| `agents/` | Subagents: `contract-reviewer`, `security-reviewer`, `run-debugger` (these three keep project memory in `agent-memory/<name>/MEMORY.md`), `test-writer`, `docs-syncer`. |
| `commands/` | Short slash commands: `/check`, `/migrate`, `/review`, `/sync-docs`. |
| `output-styles/` | `/output-style`: `Harness Engineer` (terse, cites file:line, explicit verification) and `Onboarding Mentor` (explains the why for new teammates). |
| `workflows/` | Multi-agent runs (ask Claude to "run the review-branch workflow"): `review-branch` (four review lenses, then adversarial verification), `audit-contracts` (whole-repo contract consistency). |

When a convention changes, update the rule, skill or agent memory in the same change. A rule that no longer matches the code is worse than none (`docs` rule, `/sync-docs`).
