# WebBlock site

Generated by the WebBlock AI harness. Do not edit this repository by hand: every harness run pushes a full snapshot and overwrites manual changes.

- `puck-data.json`: every page (path, SEO fields and Puck content), served by `app/[[...slug]]/page.tsx`. Content-only edits change only this file.
- `/products/<slug>`: a detail page for every product, also served by `app/[[...slug]]/page.tsx`. Each product card links to it.
- `/portal`: the product portal. Owners sign in through WebBlock single sign-on (Keycloak; `lib/portal-auth.ts`) and add, hide or delete products; changes appear on the site immediately.
- `components/blocks/`: one React component per Puck block type.
- `components/registry.tsx`: maps Puck block types to components. The harness regenerates it on every run.
- `db/schema.ts`: the site's tables in WebBlock's shared `site_data` database schema, as Drizzle tables. Its `products` table is the catalog the site shows and the portal edits (`lib/products.ts`). WebBlock creates the tables; the site cannot change them.
- `db/seed.sql`: the starting data (business profile and products). WebBlock applies it on every deploy; it only fills tables that have none of this site's rows, so it keeps products added in the portal.

## Running it

The WebBlock platform builds the `Dockerfile` (a standalone Next.js server on port 8080, running as UID 65532 with a read-only file system) and passes the database as the libpq variables `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` and `PGSSLMODE`, plus the site's tenant token `WEBBLOCK_SITE_TOKEN`. The data lives in WebBlock's shared database, where row-level security shows every site only its own rows (`lib/db.ts`). `GET /healthz` answers 200 while the server is up; `GET /readyz` answers 200 only when the database does.

With database settings (those variables, or `DATABASE_URL`, plus `WEBBLOCK_SITE_TOKEN`), the site reads its products from Postgres on every request; without them, it shows the products from `puck-data.json` and the portal is disabled. The portal also needs the single sign-on settings that WebBlock sets when it deploys the site: `KEYCLOAK_ISSUER`, `KEYCLOAK_CLIENT_ID`, `KEYCLOAK_CLIENT_SECRET` and `SITE_URL`.

```bash
export PGHOST=localhost PGPORT=5432 PGDATABASE=webblock PGUSER=webblock_site PGPASSWORD=password PGSSLMODE=disable
export WEBBLOCK_SITE_TOKEN=...   # from WebBlock: the site_env of its deploy
export KEYCLOAK_ISSUER=https://auth.example.com/realms/webblock
export KEYCLOAK_CLIENT_ID=webblock-site-<projectId>
export KEYCLOAK_CLIENT_SECRET=...
export SITE_URL=http://localhost:8080
npm install
npm run dev        # http://localhost:8080
```

Or as the platform runs it:

```bash
docker build -t site .
docker run --read-only --tmpfs /tmp --user 65532:65532 -p 8080:8080 -e PGHOST=... -e PGDATABASE=... -e PGUSER=... -e PGPASSWORD=... -e PGSSLMODE=disable -e WEBBLOCK_SITE_TOKEN=... site
```
