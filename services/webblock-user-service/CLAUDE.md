# WebBlock — user-service

This repo is **only user-service** (spec name: account-service) of WebBlock, an AI no-code website builder.
Team-wide rules and specs come from the template repo `Endy0611/clean_architecture_webblock_backend`
(`docs/specs/` is copied here). Explain things in simple, short English; keep keywords as they are.
Progress and the task list: `docs/PLAN.md` (read it first).

## What this service owns
- Tables `account_users`, `account_user_status_changes` — columns must match `docs/specs/data-dictionary.md`
  **exactly** (the team treats the data dictionary as fixed). Do not add columns without team approval.
- Registration, email OTP, forgot/reset password, profile (full name, photo), admin user list + suspend/unsuspend.
- Talking to the Keycloak **Admin API** (only this service does that).
- API prefix `/api/user/v1`, port 8081. Base package `org.kshrd.webblock.user`, clean architecture layout
  (`presentation` / `application/<feature>` / `domain` / `infrastructure`) — see `.claude/rules/java-layout.md`.

## Decisions already made (do not change without asking)
- **Keycloak** (dev): admin console `https://kc-admin.roa-dev.digital`, public host `https://auth.roa-dev.digital`.
  Realm `webblock`. Issuer: `https://auth.roa-dev.digital/realms/webblock`.
- Realm roles are lowercase: `user` (default for everyone), `admin` (staff only, created by the dev team,
  **never** through registration).
- Clients: `webblock-web` (confidential, standard flow + PKCE S256; direct access grants ON only in dev for testing),
  `webblock-auth-admin` (service account with `realm-management` `manage-users` + `view-users`, used by this service).
- Realm login settings: email as username, login with email, duplicate emails OFF, user registration OFF,
  forgot password OFF, verify email OFF (our OTP does this), `lastName` not required.
  Password policy: length 8, 1 upper, 1 lower, 1 digit, not username. Brute force: lockout temporarily after 5 failures.
- **Sign in** happens on **Keycloak's login page** (later styled like the Figma design), so SSO works.
  **Register** and **Forgot password** use our own Next.js pages + this service, with a **6-digit email OTP**.
- **OTP codes live in Redis** (no OTP table). Store only a hash, expire after a few minutes, max 5 wrong tries,
  60 s wait before resend, delete after use. Never log OTPs.
- After a correct OTP, return a short single-use **verification token**; `register/complete` and `password/reset`
  only work with it (otherwise anyone could skip the OTP).
- **One account, two login methods**: same email via Google and via email/password = one Keycloak user.
  Register on an email that exists only through Google (no password) → after OTP, add a password to that same user.
  Email that already has a password → "You already have an account. Sign in or reset your password."
- Forgot password always answers the same message whether the email exists or not.
- **Profile photo** is NOT in our table: the file goes to **RustFS** (S3-compatible), and its URL is saved in the
  Keycloak user attribute `picture`. Users can upload, change and remove it. Google picture is imported only on
  first login (sync mode Import), so it never overwrites an uploaded photo. UI fallback: uploaded → Google → initials.
- Suspending a user sets `status = SUSPENDED`, writes `account_user_status_changes`, and disables the user in Keycloak.
- Generated websites are public showcases. Each site has a **Business Portal at `/portal`** (generated by the AI
  service) that signs the owner in through Keycloak (SSO + PKCE). Later this service will create one Keycloak
  client per site (redirect `https://<subdomain>.webblock.com/portal/callback`) when provisioning deploys it.

## Main flows (from the team's auth workflow diagram, with our fixes)
- **Register (email):** full name + email → is valid? → send 6-digit OTP → verify (resend allowed) →
  create password + confirm → create account (Keycloak user, `emailVerified=true`, role `user`) → go to Sign in.
- **Sign in:** Keycloak login page (email + password, or Continue with Google) → token → frontend reads roles:
  `admin` → Admin Portal, otherwise → User Dashboard. Suspended users cannot sign in or refresh.
- **Continue with Google:** Keycloak brokers Google (`kc_idp_hint=google`). A new Google user gets an account
  automatically. Same "Is admin?" check as normal sign in (the original diagram forgot it on the Google path).
- **Forgot password:** email → (same reply whether it exists) → OTP → verify → new password + confirm → update
  password → log out all sessions → Sign in.
- **Example (Sara):** Google first, later registers with the same email → OTP → sets a password on the SAME account.
  Later she clicks **Portal** on a website card → new tab `https://<subdomain>.webblock.com/portal` → Keycloak sees
  she is already signed in (SSO) → back to the portal with a token → the site's own API checks the token
  (issuer + `sub` == site owner, given to the site as env var by provisioning) → she adds/edits/deletes products.
  Visitors of the website never sign in.

## From the UI (Figma)

- Google users can optionally set a password (inline "Set password" form). Email users see "Google not connected"
  with an option to connect Google.

## Running locally
Needs Cloudflare One Client ON to reach the dev database. Env vars (never commit values):
`DB_URL` (`jdbc:postgresql://<host>:<port>/account`), `DB_USER`, `DB_PASSWORD`,
`KEYCLOAK_ISSUER_URI`, and `EUREKA_CLIENT_ENABLED=false` when discovery-service isn't running.
Commands: `./gradlew.bat bootRun`, `./gradlew.bat test`, `./gradlew.bat build`. Swagger: `http://localhost:8081/swagger-ui.html`.

## Hard rules
1. Never edit an applied Flyway migration (`src/main/resources/db/migration/V<yyyyMMddHHmm>__*.sql`). Add a new one.
2. Enum values exactly as in `docs/specs/status-flows.md` (`ACTIVE`, `SUSPENDED`; reasons `ABUSE`, `FRAUD`, `OWNER_REQUEST`, `OTHER`).
3. Never commit or read secrets / `.env*`. Config from env vars only.
4. Never read another service's database. Call its API.
5. Branches: `feat/user-service-<what>` from `dev` → pull request into `dev` → at the deadline, pull request `dev` → `main`.
   Never push straight to `dev` or `main`. Small changes, run tests before saying "done".
