# Project constitution

Version 9

The non-negotiable rules of the Project service. Every design, plan and review is checked against each article.
Cite an article as `Art. N` (for example `Art. III`). The details live in the files each article links; this page
does not copy them.

## How it is used

- A change note names an article only when the change could break it; a design file has the full table, one row
  per article. A reviewer, when one runs, checks them again.
- A conflict stops the work. The lead takes it to the owner, who either changes the work or amends this page.
- Sources of truth stay as `.claude/CLAUDE.md` lists them: Notion first, then the spec, the decision records and
  the repo files. This page says which rules may never bend; it does not replace those sources.

## Article I: Lean flow, code first

- Small batches. One change per branch, merged within a day where it can be. A change is one FR, or one small
  group of FRs that only make sense together.
- Two owner gates: the owner agrees the change note before code (a one-line yes is enough) and the owner merges.
- The change note is a few lines in the chat: the closest FR or TR ID, what changes, the tests. A design file is
  written only for a new service, a new or changed contract between services, or a schema change. A decision
  record is written only when a rule is set that later work must follow.
- Every commit cites the closest existing FR or TR ID. A new ID is added to the spec only for a new user-visible
  feature or a new contract between services; a technical change cites an existing ID and adds none.
- Code comes first. Tests are written with the code and named by their ID. Docs change only when a fact people
  run or rely on changes: a runbook step, a README command, a contract between services, or a rule later work
  must follow. No commit only rewraps lines or rewords text.
- Drift stops work: the implementer reports both sides; the owner decides; then the spec changes first.
- One fix round per change. A finding still open after it becomes a backlog item with its ID, or goes to the owner
  if it is High.
- The direction check and the QA sweep run once per phase, not per branch.
- Enforced by: `.claude/rules/spec-driven.md`, the commit ID check in `.claude/hooks/guard.py`, the gates in
  `./gradlew check`, `scripts/spec-check.py` (report only).

## Article II: Tech stack

- The stack is fixed: Java 25, Spring Boot 4.1.1, Spring Modulith 2.1.1, Gradle through the wrapper, PostgreSQL 18
  with Flyway, RabbitMQ with the Namastack outbox. Exact versions: `.claude/TECH_STACK.md`.
- Calls between services may use gRPC: grpc-java with protobuf, stubs generated by `protoc` from the contracts
  pinned by full commit SHA from `web-block-contracts` (`contracts.lock`, copied into `contracts/` only by
  `scripts/contracts-sync.sh`).
- A new or changed dependency needs the owner's approval first. It is open source, at least 14 days old, pinned
  exactly in `gradle/libs.versions.toml` and `gradle.lockfile`, covered by `gradle/verification-metadata.xml`,
  recorded in `.claude/docs/dependency-versions.md`, and `scripts/osv-scan.sh` is clean.
- First-party WebBlock packages (`web-block-commons`) are exempt from the open-source and 14-day rules above. Each is
  pinned to an exact released version built from a reviewed, annotated tag on that repository's `main` whose own gates
  passed (tests, OSV scan, age check of its third-party pins), covered by `gradle/verification-metadata.xml` and
  recorded in `.claude/docs/dependency-versions.md`, and fetched with a read credential that never enters a lockfile,
  an image layer or the repository. Its own dependencies keep every rule of this article.
- Adding or replacing a part of the stack (a language, framework, database, broker, build tool or a major version)
  needs an amendment of this article. A minor or patch upgrade follows the dependency rule above.
- Enforced by: the owner approves each version before the change; the `project-gates` skill locks and verifies the
  dependencies; `scripts/osv-scan.sh`; decision `0011`.

## Article III: Architecture limits

- Java layout of Notion "Web Block architecture" 6.1, layer first: `presentation`, `application`, `domain` and
  `infrastructure`, each split by type folder and feature (decision `0016`); `common` keeps its own four layers.
  Features are not Spring Modulith modules. Request, response and validation types sit in `application/<feature>/`
  (`request`, `response`, `validation`), as 6.1 shows. Request, response and mapping are per feature and never shared.
- The domain holds entities and rules and has no repository. Spring Data repositories live in
  `infrastructure/persistence/<feature>`; the handlers of the same feature use them directly. Other features are
  used through their `application` classes. Project is not CQRS.
- ArchUnit rules (`ArchitectureRulesTest` and the rule tests in `architecture/`) are never loosened; adding or
  tightening one needs the owner.
- The databases match Notion "2 · Project" and "6 · Shared catalog" 100%: every table, column, type, NULL rule,
  enum value, index, constraint, role and grant, and nothing more. No extra index, column, grant or constraint.
  Migrations are forward-only and never edited once applied.
- PostgreSQL holds the truth. A change and its event are stored in one transaction and leave through the Namastack
  outbox; handled messages are recorded once. One generation request in flight per project; saves carry the
  `edit_revision` they read.
- Service boundaries: Project owns websites, pages, generation contracts and requests, the catalog schema and site
  registration, and its events. Another service's endpoint, event, audience or table is never invented.
- Auth model: the Istio gateway checks the token, then the first service checks it again (Keycloak key set, RS256,
  issuer, audience `project`, `typ` Bearer, `exp`, `nbf`). Calls between services carry only `x-user-id` over mTLS,
  trusted only from callers the mesh `AuthorizationPolicy` allows. Tokens are never forwarded, logged or put in an
  error. `/internal/**` takes no token: the mesh policy guards it.
- Not the owner is 404: a caller who may not see a project, page or request gets `PROJECT_NOT_FOUND`, never 403,
  and the internal access check answers `allowed: false`, reason `NOT_FOUND` for an unknown project and
  `NOT_MANAGER` for a caller who is not the owner; every caller maps both to 404 `PROJECT_NOT_FOUND` toward the
  user. The one recorded exception: a create
  `PUT` on a taken project ID answers 409 `PROJECT_ID_CONFLICT` (decision `0007`). Ownership is checked in the
  services, never by method security.
- Enforced by: `.claude/rules/java-code.md`, `.claude/rules/migrations.md`, the `db-notion-audit` skill, decisions
  `0001`, `0002`, `0004`, `0007` and `0016`, `.claude/docs/contracts/authentication-contract.md`,
  `JwtDecoderConfig`.

## Article IV: Coding conventions

- The Java rules are `.claude/rules/java-code.md`; `.claude/CLAUDE.md` section 3 gives the short form.
- Enforced by: Spotless, Error Prone and the ArchUnit tests in `./gradlew check`.

## Article V: Testing and quality

- Every change ships with tests in the same commit, each naming its ID (`@DisplayName("FR-12.3: ...")` or
  `fr12_3_...`). A bug fix has a test that was seen failing before the fix.
- The Gradle gates pass and are never lowered: `spotlessCheck`, `test`, `integrationTest` and the coverage rules in
  `check`. No `@Disabled`, no skipped suite. A check not run is "not run", never "passed".
- Coverage: 70% of lines overall, 80% in `common`, 80% in each `application.*.handler.*Service` and
  `domain.*.model.*Entity` class. Never add an exclusion to pass.
- PMD, CPD and SpotBugs are report-only QA tools (decision `0009`). They become a gate only by a new decision.
- Enforced by: `.claude/rules/testing.md`, the `project-gates` and `qa-sweep` skills.

## Article VI: Safety guardrails

- The real cluster (DOKS) is read-only for agents: reads are allowed, every change is denied and is a command
  written for the owner, and no Secret value is printed. Kind runs only through Provisioning's local targets in an
  owner-given slot.
- No secrets: never read, print, write or commit a secret value, `.env` file or dev token file, and never open a
  kubeconfig (kubectl and helm load it themselves for a read).
- Prototype stand-ins (dev tokens, the Payment stand-in) exist only in the `prototype` profile. Production runs JWT
  only, holds no migrator password and never migrates in-process.
- No push. No agent merges into `main`; the owner merges and pushes.
- The Notion database design pages are read-only, except "2 · Project" and "6 · Shared catalog": the lead edits
  those two on the owner's word, before the migration that follows them. Other services' pages stay read-only.
- The hooks are on and are never worked around: `.claude/hooks/guard.py` blocks or asks, `reviewer_writes.py`
  keeps reviewers read-only. Edits to this page, the hooks and `settings.json` ask the owner.
- Enforced by: `.claude/CLAUDE.md` section 0, `.claude/hooks/`, `ProfileGuard`, ArchUnit
  `standInsAreOnlyInThePrototypeProfile`, decision `0005`.

## Article VII: Docs

- Docs state current facts only; git history is the record. No dates of changes, change logs or provenance tags.
- Plain English, no em or en dashes, lines at most 120 characters.
- Enforced by: `.claude/rules/docs-style.md`, `.claude/hooks/post_edit_check.py`.

## Article VIII: Agents

- One implementer at a time in the shared tree.
- A review runs only when the change is security-sensitive: tokens, `SecurityConfig`, ownership answers,
  `/internal` or mesh rules, secrets, the guard, the cluster, dependencies, migrations or grants. Then one
  independent `security-reviewer` pass (and the `db-notion-auditor` for a migration or grant). Any other change
  merges on green gates after the owner reads the diff. An agent never reviews its own work, and reviewers write
  only their reports. A re-review only when the review found something High.
- The owner agrees the change note and merges. Agents do not start other agents.
- Enforced by: `.claude/WORKFLOW.md`, `.claude/agents/README.md`, `reviewer_writes.py`.

## Amendments

Only the owner amends this constitution. An amendment raises the version number at the top by one and changes the
articles in place. No dates and no change notes: git history is the record. An agent may propose an amendment in
its report; it never edits this file itself, and the guard hook asks the owner before any edit of it.
